# Task: Stryker.NET mutation testing with a ratcheting CI gate

## Description

Measure whether the tests detect a wrong implementation, not only whether they execute the
code. Establish a baseline mutation score, triage every surviving mutant, and gate CI so the
score cannot drop.

## Context for the implementer

Tool: `dotnet-stryker` 5.0.0 (Apache-2.0, released 2026-09-11, targets the .NET 10 runtime).
Pin it in a local tool manifest so CI and developers run the same version.

Mutate the four `src/` projects. Run the behaviour suites against them (Domain, Application,
Infrastructure, Api tests, plus Acceptance if task 002 has merged). Leave
`FileMutation.Architecture.Tests` out: it asserts structure, kills no behavioural mutant, and
only adds runtime.

The allocation results page, `docs/benchmarks/allocation-results.md`, is the model for the
results page: exact command, tool and runtime versions, the table, then an honest paragraph
about what the numbers do and do not show.

Two known hazards:

- `src/Directory.Build.props` turns CS1591 (missing XML doc) into an error and loads
  SonarAnalyzer plus the repo's own `FM001` analyzer. Stryker compiles mutated code with
  injected helper code; if those rules fire on it, mutants show up as compile errors and the
  score means nothing.
- `.claude/rules/sandbox-pre-mortem.md`: VSTest talks to its test host over a local socket, and
  Stryker runs VSTest many times. Inside the agent sandbox that hangs rather than erroring. Run
  Stryker outside the sandbox from the start.

## Pre-mortem

**Most likely failure:** the mutated compilation trips CS1591-as-error, SonarAnalyzer or
`FM001` on Stryker's injected code, a large share of mutants report as compile errors, and the
resulting score is recorded as if it meant something.

**Early signal:** a non-zero "compile error" count in the first run's summary, or errors under
`--diag`.

**Kill criterion:** fix through Stryker configuration only. Never relax `WarningsAsErrors` or
disable analyzers in `src/` to make the tool pass. If it is not solved within 45 minutes, stop
and report with the `--diag` output.

## Acceptance Criteria
- [ ] `dotnet tool restore && dotnet stryker` runs from a clean clone using the pinned 5.0.0
- [ ] Zero mutants reported as compile errors, or each remaining one explained in the results page
- [ ] `docs/quality/mutation-results.md` records the exact command, versions, runtime and the score per project (killed, survived, timeout, no coverage)
- [ ] Every surviving mutant is triaged in the results page as either an equivalent mutant (with the reason) or a real test gap; each real gap is filed as its own issue, not fixed in this PR
- [ ] `mutation.yml` runs on every pull request to `main` and on `workflow_dispatch`, and uploads the HTML report as an artifact
- [ ] `thresholds.break` is set to the measured baseline score rounded down, so the score can only ratchet up
- [ ] The gate is shown to fail on purpose: on a scratch branch, delete one assertion that kills mutants and confirm the job goes red (link the run in the PR)
- [ ] Full-run wall time on `ubuntu-latest` is reported. If it is 10 minutes or less, the PR proposes adding the job to required status checks; if more, the PR switches pull requests to `--since:main` and adds a weekly scheduled full run. Changing branch protection needs the owner's go (AGENTS.md), so this is a proposal, not a change made by the implementer

## Verify with

```bash
dotnet tool restore
dotnet stryker --config-file stryker-config.json
```

## Do not

- Do not edit `ci.yml`; the mutation job lives in its own workflow.
- Do not add tests in this PR to raise the score. Surviving mutants become issues; the baseline records the honest starting point.
- Do not include `benchmarks/` or `tools/` in the mutated set.
