# Task: Gherkin acceptance scenarios for US-1 and US-2

## Description

Turn the PRD's US-1 and US-2 acceptance criteria into executable Gherkin scenarios that run
against the real host through `WebApplicationFactory`. The audience is the product owner: a
feature file should read as the API's promise, and each PRD criterion should be traceable to
the scenario that proves it.

## Context for the implementer

Framework: the one ADR-0010 settles (proposed: Reqnroll 3.3.4 with `Reqnroll.xUnit`, which
depends on `xunit.core` 2.8.1; the repo runs xunit 2.9.3). Read ADR-0010 before starting.

Source of truth for the scenarios: `.claude/prds/file-mutation-api.md`, sections "US-1: Upload
and receive a mutated file" and "US-2: Reject invalid uploads predictably". Each checkbox
there is one criterion.

The host factory already exists: `tests/FileMutation.Api.Tests/FileMutationApiFactory.cs`,
with deterministic fakes in `tests/FileMutation.TestCommon/DeterministicFakes.cs`. Share the
factory, do not copy it. Moving it into `FileMutation.TestCommon` is the preferred route; if
that forces an ASP.NET Core test-host dependency onto something that should not carry it,
reference `FileMutation.Api.Tests` instead and say why in the PR.

`tests/` projects do not inherit `src/Directory.Build.props`, so the analyzers and
warnings-as-errors settings that apply to `src/` do not apply to generated step code.

Scenario language is business-level. The Then step may name the status code, because it is the
contract. Steps must not mention multipart boundaries, header names or byte arrays.

## Pre-mortem

**Most likely failure:** the step definitions turn into a second integration suite written in
prose. Steps get phrased as HTTP scripts, the product owner cannot read them, and they drift
from `FileMutateEndpointTests` because two suites now assert the same behaviour.

**Early signal:** any step text containing "multipart", "boundary", a header name or a byte
value; or a scenario whose assertion already exists verbatim in `FileMutateEndpointTests`.

**Kill criterion:** if the Reqnroll generator does not build and discover tests on .NET SDK
10.0.301 with xunit 2.9.3 within 45 minutes, stop and report. Do not switch framework without
updating ADR-0010 first.

## Acceptance Criteria
- [ ] Every US-1 and US-2 acceptance criterion in the PRD maps to exactly one scenario, tagged `@US-1` or `@US-2`; a criterion that cannot be expressed over HTTP is listed in the feature description with the reason
- [ ] The 415 cases (`.json`, `.csv`, `.docx`, wrong declared type, invalid UTF-8) are one Scenario Outline with an Examples table, not five scenarios
- [ ] Rejections assert a ProblemDetails body, not only the status code
- [ ] Clock and random sequence are deterministic, so the success scenario asserts the exact returned content and filename
- [ ] Scenarios run inside `dotnet test` and in CI with no workflow change
- [ ] Each scenario is shown to fail when its behaviour is broken (one planted break per feature, listed in the PR, not committed)
- [ ] Integration tests that became exact duplicates are removed and named in the PR; branch coverage not lower than before
- [ ] No generated step-binding code committed
