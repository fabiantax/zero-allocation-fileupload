# Task: API host + OpenAPI/Scalar UI + CI skeleton

## Description

Stand up the solution with a running .NET 10 API host and a browser-reachable OpenAPI UI (Scalar), plus the CI workflow that will gate every later PR. No domain logic — this exists so there is something demonstrable before any feature work starts.

## Context for the implementer

- Package choice (OpenAPI/Scalar packages, whether AOT is even on) is not open for debate here — task 000 already ran the AOT publish spike and recorded the decision in `docs/adr/0001-native-aot.md`. Build against exactly what that ADR selected; if it says AOT was dropped, don't force `PublishAot=true` here either.
- The coverage gate goes in now, but at **threshold 0** — it only needs to exist and read the branch figure, not enforce a real bar yet. Task 012 raises it to 80%. Wire it to branch coverage from the start; reading the line figure here silently breaks the ratchet in 012 (see .claude/rules/dotnet-conventions.md).
- Trap: this task's own `dotnet publish -p:PublishAot=true` has to succeed against the *real* project structure you scaffold, not just recheck the throwaway spike from 000 — the spike proved feasibility, not that this project's `Program.cs` and package references are wired correctly.

## Do not

- Do not re-run the AOT/Scalar feasibility spike or second-guess task 000's ADR — implement against its decision.
- Do not set the coverage gate threshold above 0 — that's task 012's job; a premature 80% gate blocks every PR before there's any real coverage to hit.
- Do not add domain logic or endpoints beyond the stub — this task is host + CI skeleton only.

## Technical Details

- `dotnet new sln`, `dotnet new webapi` (minimal API — MVC controllers are not AOT-supported), `dotnet new xunit`
- OpenAPI document via built-in `Microsoft.AspNetCore.OpenApi`; browser UI via `Scalar.AspNetCore`, which serves a static shell that fetches the document — minimal reflection surface. Verify by publishing, not by assumption: the ticket requires a working Swagger-style UI, so if AOT and the UI genuinely conflict, the UI requirement wins and AOT is dropped with the reason recorded in an ADR
- Solution layout: `src/`, `tests/`, `benchmarks/`. Test projects are named `{project}.Tests` so `*.Tests` greps cleanly
- CI uses `actions/setup-dotnet` pinned to the .NET 10 SDK (10.0.301 confirmed available locally)
- Keep `Program.cs` thin — it becomes the composition root in later tasks

## Risks

- AOT + OpenAPI UI compatibility is the one unknown in this task. It is settled by a publish, not a discussion — do that spike before writing anything else, because the package choice is expensive to reverse once endpoints are documented against it.
