# Task: Domain contracts and ports

## Description

Land the shared contract surface — value objects, ports, and API DTOs — so later tasks can be built in parallel against a stable, compiling interface. Interfaces and types only; no implementations.

This is the task that unblocks the parallel wave, so it stays deliberately small and merges fast.

## Context for the implementer

- This task's whole purpose is to unblock the parallel wave (003 depends on it directly, later tasks indirectly) — once merged, its public surface, especially the mutation policy signature and the port interfaces, is what those tasks code against. Get the signature right now; changing it later means touching already-in-flight parallel branches.
- The mutation policy must be a pure function over `Span<byte>`/`Span<char>` with no `Stream`/`PipeReader`/`PipeWriter` in its signature — task 003 is the one that adapts `Pipelines` into spans and calls this function. Don't have it accept or return a stream type "for convenience"; that pushes I/O into Domain and breaks the split 003 depends on (see .claude/rules/dotnet-conventions.md).
- **The acceptance rule is the important piece of this task.** It goes in Application as a plain function over content plus declared metadata, returning a result. No `HttpContext`, no `IFormFile`, no `HttpRequest` — if it cannot be called from a console app it is in the wrong place.
- No registry, no capability enum, no second mutator port. One `IFileMutator`, one acceptance function. Dispatch is added when a second format exists, not in anticipation of one.

## Acceptance Criteria
- [ ] `FileMutation.Domain` project with no framework or Infrastructure references
- [ ] `FileName` value object: always-valid (validates in its constructor), sanitises the incoming name, rejects path traversal, preserves the original for the download response
- [ ] Mutation **policy** expressed as a pure function over `Span<byte>`/`Span<char>` — given a clock reading and a random sequence, it writes the suffix. No streams, no pipes, no I/O types in its signature

- [ ] Validation results are returned, not thrown — a rejected upload is an expected outcome, not an exception

## Do not

- Do not add an aggregate root or an entity with identity — this operation has no lifecycle to model.
- Do not put acceptance rules in the endpoint, or take an `IFormFile`/`HttpRequest` parameter. The API is an entry point to the rule; it does not own it.
- Do not add a second seam for *what data gets appended*. That is a parameter on `MutationContext`, not an interface — see the epic's modelling stance.
- Do not implement `IFileMutator` or `IRandomSequenceGenerator` here — interfaces and value types only; implementations are later tasks (003+).
- Do not add a repository, storage, or persistence port of any kind. Upload, mutate, return — nothing is written anywhere.
- Do not let DTOs leak into Domain, or have Domain/Application reference Infrastructure or Api.

## Technical Details

- **Policy vs plumbing split**: Domain owns *what* gets appended and in what format; Infrastructure (task 003) owns the `Pipelines` mechanics that feed bytes through it. This keeps Domain I/O-free per Clean Architecture and makes the hot path testable with no streams at all
- Ports that do cross an I/O boundary are stream/pipe-oriented (`PipeReader`/`PipeWriter`), never `byte[]`, so no implementation is forced to buffer a whole file
- `IFileMutator` receives `TimeProvider` and `IRandomSequenceGenerator` by injection rather than reading the clock or RNG itself
- **No aggregate root is introduced.** This operation has no identity, lifecycle, or cross-entity invariant. Adding `UploadedFile` as an aggregate would be DDD ceremony without a domain reason
- The acceptance rule is **variant-agnostic**: both the simple service (`main`) and the CQRS branch (013) call the same function. CQRS supplies dispatch; Application keeps the rule. Without this the variants fork their validation and 013's "same test suite passes unchanged" criterion becomes unmeetable
