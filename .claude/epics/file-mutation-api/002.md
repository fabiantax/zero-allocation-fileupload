# Task: Domain contracts and ports

## Description

Land the shared contract surface — value objects, ports, and API DTOs — so later tasks can be built in parallel against a stable, compiling interface. Interfaces and types only; no implementations.

This is the task that unblocks the parallel wave, so it stays deliberately small and merges fast.

## Context for the implementer

- This task's whole purpose is to unblock the parallel wave (003 depends on it directly, later tasks indirectly) — once merged, its public surface, especially the mutation policy signature and the port interfaces, is what those tasks code against. Get the signature right now; changing it later means touching already-in-flight parallel branches.
- The mutation policy must be a pure function over `Span<byte>`/`Span<char>` with no `Stream`/`PipeReader`/`PipeWriter` in its signature — task 003 is the one that adapts `Pipelines` into spans and calls this function. Don't have it accept or return a stream type "for convenience"; that pushes I/O into Domain and breaks the split 003 depends on (see .claude/rules/dotnet-conventions.md).
- `IFileRepository` looks unused by anything else in this epic — no persistence task exists yet. It's intentionally there for future extensibility (PRD OQ-1/OQ-2), not dead code to prune.
- Do not add a second mutator port. `IFileMutator` already has the right shape (`PipeReader` in, `PipeWriter` out), so format identity goes **on it** as `Format` and `Capability`; a parallel `IFileFormatMutator` would differ from it in name only.
- `MutationCapability` is not decoration. It is the only place the design admits that a future container format cannot stream. Dropping it makes every adapter look uniform while hiding an NFR-1/NFR-3 breach — which is precisely the failure it exists to prevent.

## Acceptance Criteria
- [ ] `FileMutation.Domain` project with no framework or Infrastructure references
- [ ] `FileName` value object: always-valid (validates in its constructor), sanitises the incoming name, rejects path traversal, preserves the original for the download response
- [ ] Mutation **policy** expressed as a pure function over `Span<byte>`/`Span<char>` — given a clock reading and a random sequence, it writes the suffix. No streams, no pipes, no I/O types in its signature
- [ ] Ports defined: `IFileMutator`, `IFileRepository`, `IRandomSequenceGenerator`
- [ ] `IFileMutator` carries `FileFormat Format` and `MutationCapability Capability` (`Streaming` | `BufferedRewrite`); its `PipeReader`/`PipeWriter` signature stays uniform across both capabilities, so a buffering adapter does its buffering internally rather than changing the call shape
- [ ] `IFileMutatorRegistry` resolves filename + declared content-type to an `IFileMutator` and **returns a result** for an unsupported format — it does not throw, and it does not fall back to a default mutator
- [ ] `MutationContext` carries the values to append (clock reading, random sequence) as data rather than as magic strings inside the policy — the ticket's "data *like* a date and a random sequence" is illustrative, so the payload is a parameter
- [ ] `FileMutation.Application` project referencing Domain only, with the use-case interface for mutate-a-file
- [ ] Validation results are returned, not thrown — a rejected upload is an expected outcome, not an exception
- [ ] API request/response DTOs defined with XML docs and OpenAPI annotations; DTOs live at the Api boundary and are never referenced by Domain
- [ ] Unit tests in `FileMutation.Domain.Tests` cover `FileName` rules (valid, traversal attempt, empty, non-ASCII) and the mutation policy against a stack-allocated span
- [ ] Solution builds with Domain referencing nothing but the BCL

## Do not

- Do not add an aggregate root or an entity with identity — this operation has no lifecycle to model.
- Do not give `IFileMutatorRegistry` a default or fallback mutator. An unresolvable format must surface as a rejection; silently falling back to the plain-text mutator would corrupt a file the endpoint promised to reject.
- Do not add a second seam for *what data gets appended*. That is a parameter on `MutationContext`, not an interface — see the epic's modelling stance.
- Do not implement `IFileMutator`, `IFileRepository`, or `IRandomSequenceGenerator` here — interfaces and value types only; implementations are later tasks (003+).
- Do not let DTOs leak into Domain, or have Domain/Application reference Infrastructure or Api.

## Technical Details

- **Policy vs plumbing split**: Domain owns *what* gets appended and in what format; Infrastructure (task 003) owns the `Pipelines` mechanics that feed bytes through it. This keeps Domain I/O-free per Clean Architecture and makes the hot path testable with no streams at all
- Ports that do cross an I/O boundary are stream/pipe-oriented (`PipeReader`/`PipeWriter`), never `byte[]`, so no implementation is forced to buffer a whole file
- `IFileMutator` receives `TimeProvider` and `IRandomSequenceGenerator` by injection rather than reading the clock or RNG itself
- `IFileRepository` stays minimal (persist + retrieve by id); it exists for extensibility (PRD OQ-1/OQ-2), not because the ticket requires storage
- **No aggregate root is introduced.** This operation has no identity, lifecycle, or cross-entity invariant. Adding `UploadedFile` as an aggregate would be DDD ceremony without a domain reason
- The format seam is **variant-agnostic**: it lives in Domain so the simple service (`main`) and the CQRS branch (013) both dispatch to the same adapters. CQRS supplies dispatch; Domain keeps the policy. Without this, the two variants fork the mutation logic and 013's "same test suite passes unchanged" criterion becomes unmeetable
