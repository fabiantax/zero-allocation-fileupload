# Task: Unit tests for domain, application and infrastructure

## Description

Write unit tests for the Application-layer use case and the Api-layer validation logic, exercised in isolation with no ASP.NET Core types and no real I/O — plus confirm the Domain and Infrastructure suites 002 and 003 already specify are complete and green.

Rescoped from the original combined testing task: unit tests and the integration-test-plus-coverage-gate work are different concerns. Integration tests (`WebApplicationFactory`, rejection-path assertions, `Content-Disposition`) and the branch-coverage CI gate now live in 012.

## Context for the implementer

Domain (002) and the mutation engine (003) already specify their own unit tests as acceptance criteria in those tasks — do not duplicate that work here. This task's actual surface is the Application use case and the Api endpoint's validation logic (size/type/decode checks), tested directly rather than through HTTP — 004 only asks for "tests written and passing" generically, so the specifics belong here. Put the deterministic `TimeProvider`/`IRandomSequenceGenerator` fakes somewhere shared (e.g. `tests/FileMutation.TestCommon/`) rather than per-project — 012's integration tests reuse the same fakes. 012 depends on this task and is what raises the coverage gate to 80% branch; this task does not touch CI or coverage at all.

## Pre-mortem

**Most likely failure:** Tests are written against the implementation rather than the behaviour, so they pass, add coverage, and would still pass if the logic were reverted.

**Early signal:** A test that never fails when you deliberately break the code it covers. Break it once on purpose.

**Kill criterion:** Coverage climbs while mutation-style spot checks keep passing — that means the suite measures execution, not correctness.
