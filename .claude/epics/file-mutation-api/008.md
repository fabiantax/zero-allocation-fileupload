# Task: BenchmarkDotNet allocation proof

## Description

Measure and record what the mutation path actually allocates. Coverage proves the code is exercised; it says nothing about allocation — this is the evidence behind the zero-allocation claim.

## Context for the implementer

BenchmarkDotNet's default job already refuses to run against a Debug configuration or an in-process host — if it errors about optimizations, that guardrail is working; don't silence it with `[DisableOptimizations]` or a custom in-process job. Run via `dotnet run -c Release --project benchmarks/FileMutation.Benchmarks`, not `dotnet test` — the project is deliberately excluded from the test suite and its coverage gate. The trap: every run writes a full `BenchmarkDotNet.Artifacts/` directory (logs, multiple report formats) — commit only the extracted summary table into `docs/`, never that directory.

## Pre-mortem

**Most likely failure:** BenchmarkDotNet never actually runs — it generates, builds and spawns a child process per benchmark, which the sandbox blocks — and the absence of a measurement is read as 'nothing to report'.

**Early signal:** No `BenchmarkDotNet.Artifacts/` directory, or a summary table with no rows. Silence here is failure, not success.

**Kill criterion:** If it cannot run outside the sandbox either, record that the allocation claim is unmeasured rather than shipping the claim unbacked.

## Do not

- Do not commit the `BenchmarkDotNet.Artifacts/` directory — extract and commit only the summary table.
- Do not run or report numbers from a Debug build or an in-process toolchain — that is not evidence of allocation behaviour.
- Do not fold this project into the coverage-gated `dotnet test` run.

## Technical Details

- Benchmarks run in Release, out-of-process, with sufficient warmup — a debug-build or in-proc number is not evidence
- Commit the summary table, not the full artifact directory
- If a regression gate is wanted later, this is where a threshold assertion would attach; not in scope now
