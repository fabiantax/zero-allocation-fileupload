# Task: ADRs, README, XML documentation pass

## Description

Write down the decisions and make the repository readable to a reviewer arriving cold. The assignment is explicitly judged on approach and design choices, so the reasoning is part of the deliverable, not overhead.

## Context for the implementer

This task documents decisions made elsewhere — it does not make them. The Native AOT ADR content depends on task 000's spike outcome (adopt or drop) and the CQRS mediator ADR depends on task 009's evaluation; if either hasn't landed yet, write the ADR for what's already decided rather than guessing the outcome. The likeliest trap: an XML doc `<see>`/`<para>` link to `docs/adr/*.md` is a relative path that differs by project depth (e.g. `../../docs/adr/0001-native-aot.md` from `src/FileMutation.Domain/`) — a path copy-pasted between projects silently points at a nonexistent file instead of failing the build.

## Do not

- Do not restate the PRD's out-of-scope table — record *why* each line is out of scope, not what the line already says.
- Do not invent a decision to document — if a listed ADR topic (AOT, CQRS mediator) isn't resolved yet in its source task, stub it rather than guessing the outcome.
- Do not edit a merged ADR to reverse it — write a new numbered ADR that supersedes the old one.

## Technical Details

- ADRs are numbered and immutable once merged; a reversal is a new ADR superseding the old one, not an edit
- Keep each ADR short — context, the decision, and what it costs; a reviewer should read one in under a minute
- The out-of-scope table already exists in the PRD; the ADR records *why* each line is out of scope rather than restating the list
