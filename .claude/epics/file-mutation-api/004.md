# Task: Upload endpoint, validation, ProblemDetails

## Description

Wire the HTTP surface: accept a multipart text file upload, enforce size and type limits at the trust boundary, invoke the mutation use case, and return the mutated file as a download under its original filename. All failures surface as RFC 7807 `ProblemDetails`.

## Context for the implementer

This task codes against `IFileMutator` from 002 and does not need 003's real implementation to proceed — build and test it against a stub mutator rather than waiting on 003, despite `depends_on: [2]` making that tempting to conflate. The size limit must be enforced *before* the body is read (Kestrel limit + `MultipartBodyLengthLimit`), so the common trap is writing a redundant length check downstream that never fires because the framework already rejected the request. Route every failure through a single `IExceptionHandler`, not per-endpoint try/catch — that's what keeps every error path landing as `ProblemDetails` instead of a handful doing it and one leaking a stack trace.

## Acceptance Criteria
- [ ] `POST /files/mutate` accepts `multipart/form-data` with a single file part
- [ ] Max upload size enforced (Kestrel limit + `MultipartBodyLengthLimit`), configurable via settings
- [ ] File type validated three ways, **all** of which must pass: extension is `.txt`, declared content-type is `text/plain`, and content decodes as UTF-8 (BOM optional)
- [ ] A file that decodes cleanly but is outside the accepted set (`.json`, `.csv`, `.docx`) is still rejected with 415
- [ ] A UTF-16 file is rejected with 415 rather than mutated — appending UTF-8 suffix bytes to it would corrupt it
- [ ] The endpoint resolves its mutator through `IFileMutatorRegistry`; an unresolved format becomes a 415, never a fallback to plain text
- [ ] Response returns the mutated content via `Results.File(..., fileDownloadName:)` so `Content-Disposition` carries the original filename
- [ ] Oversized upload → 413; wrong type → 415; missing/empty file → 400; all as `ProblemDetails`
- [ ] No unhandled exception reaches the client; no stack traces in responses
- [ ] Endpoint documented in OpenAPI UI including its error responses
- [ ] Request body is streamed to the mutator — not buffered into a `byte[]` first

## Verify with

```bash
dotnet run --project src/FileMutation.Api &
curl -s -D - -o mutated.txt -F "file=@sample.txt;type=text/plain" http://localhost:5000/files/mutate
head -c 200 mutated.txt   # original content followed by the mutation suffix
# then: curl -s -o /dev/null -w '%{http_code}\n' -F "file=@huge.bin" http://localhost:5000/files/mutate  -> 413
kill %1
```

## Do not

- Do not buffer the request body into a `byte[]` before handing it to the mutator — that defeats the streaming requirement this whole task exists to enforce.
- Do not validate file type with only the extension or only the content-type header — both are attacker-controlled; the text-decode check is what catches a mislabeled binary.
- Do not accept a file merely because it decodes. Decoding is necessary, not sufficient — `.json` and `.csv` decode fine and would be silently corrupted by the append.
- Do not scatter `try/catch` across the endpoint for error mapping — one `IExceptionHandler` is the single place `ProblemDetails` gets built.

## Technical Details

- Read the multipart body with `MultipartReader` over the request `PipeReader`/body stream; hand the section straight to `IFileMutator`
- Size limit is enforced before reading the body, so an oversized upload is rejected without consuming it
- Text-decode validation must not require materialising the whole file — decode incrementally as segments arrive and fail fast on the first invalid sequence
- **Carry partial UTF-8 sequences across segment boundaries.** A multi-byte character can straddle a `ReadOnlySequence<byte>` segment edge; a decoder called per-segment as if each were complete will reject valid files, and only for inputs that happen to split a character. Use a stateful `Decoder`, not a fresh `Encoding.UTF8.GetString` per segment
- A BOM, if present, is consumed as an encoding marker and preserved in the output — it must not be treated as file content
- Exception-to-ProblemDetails mapping via `IExceptionHandler`, not try/catch scattered through the endpoint
