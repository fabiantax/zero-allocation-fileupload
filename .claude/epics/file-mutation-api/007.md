# Task: ArchUnitNET architecture rules

## Description

Make the layering claim verifiable. A small ArchUnitNET suite asserts the dependency rules the PRD states, so "adheres to DDD and Clean Code" is enforced by the build rather than asserted in a README.

Deliberately a small ruleset — enough to catch real violations, not a fitness-function framework.

## Context for the implementer

Build one `Architecture` object (via `new ArchLoader().LoadAssemblies(...)`) that loads all four project assemblies — Domain, Application, Infrastructure, Api — before writing any rule. A rule checked against a partial assembly set finds no violations and passes trivially, which looks like a clean build but proves nothing. Assert rules against that loaded `Architecture`, not against `Assembly.GetTypes()` reflection, so violations through indirect references are still caught.

## Acceptance Criteria
- [ ] `FileMutation.Architecture.Tests` project using ArchUnitNET (follows the `{project}.Tests` convention; its subject is the solution's shape)
- [ ] Rule: `FileMutation.Domain` depends on nothing outside the BCL
- [ ] Rule: `FileMutation.Application` does not depend on `FileMutation.Infrastructure` or `FileMutation.Api`
- [ ] Rule: ASP.NET Core types do not appear in Domain or Application
- [ ] Rule: port interfaces live in Domain, implementations do not
- [ ] Rules run as part of `dotnet test` and fail CI on violation
- [ ] Each rule carries a one-line comment stating the principle it protects

## Verify with

```bash
dotnet test tests/FileMutation.Architecture.Tests
```

## Do not

- Do not grow this into a general-purpose fitness-function framework — 3–6 targeted rules only.
- Do not load a single project's assembly and call the ruleset done — all four must be loaded together or cross-boundary violations go undetected.
- Do not skip proving a rule actually fails — introduce a deliberate violation once and confirm the rule catches it, per the Definition of Done below.

## Technical Details

- Keep to 3–6 rules; every added rule needs a violation it would realistically catch
- Rules are asserted against loaded assemblies, so they hold even when a reference is added indirectly
