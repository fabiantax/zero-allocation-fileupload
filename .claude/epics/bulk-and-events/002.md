# Task: Extract the multipart file-part reader from the single-file endpoint

## Description

`FileMutateEndpoint.cs` is the only multipart parser in the repo. The batch endpoint (story 006)
needs the same boundary parsing and file-part filtering. Extract it first, with zero behaviour
change, so the batch endpoint reuses it instead of copying it.

## Context for the implementer

- Move `TryGetBoundary` and `TryGetFileMetadata` out of
  `src/FileMutation.Api/Endpoints/FileMutateEndpoint.cs` into
  `src/FileMutation.Api/Multipart/MultipartFileParts.cs` with the signatures in
  `.claude/epics/bulk-and-events/contracts.md` (Api section, story 002).
- `ReadAsync` yields only `form-data` parts whose name equals `fieldName` and that carry a file
  name (`filename*` preferred over `filename`, quotes removed), exactly as today. Non-file parts
  are skipped. `InvalidDataException` and `IOException` propagate unchanged: the endpoint keeps
  mapping them to 400.
- The single-file endpoint keeps its "exactly one file part" rule and its two-phase order
  (ADR-0005): nothing is written to the response before the result is known.
- Both types are `public` so the new tests call them directly: no reflection, no
  `InternalsVisibleTo` (see the placement rules in `contracts.md`).
- `tests/FileMutation.Api.Tests/FileMutateEndpointTests.cs` (325 lines) is the safety net: it
  must pass **unmodified**.

## Files

- `src/FileMutation.Api/Endpoints/FileMutateEndpoint.cs`
- `src/FileMutation.Api/Multipart/MultipartFileParts.cs` (new)
- `tests/FileMutation.Api.Tests/MultipartFilePartsTests.cs` (new)

## Pre-mortem

**Most likely failure:** the `IAsyncEnumerable` version reads the next section before the
caller has finished the current section's body, so a file body is truncated or two bodies
interleave.

**Early signal:** the existing "second file part is rejected" test changes status, or a new
test with two parts sees the first body cut short.

**Kill criterion:** if iterator semantics fight the reader, expose
`ReadNextFilePartAsync(MultipartReader, ...)` returning `MultipartFilePart?` instead; the
signature change goes into `contracts.md` in the same PR.
