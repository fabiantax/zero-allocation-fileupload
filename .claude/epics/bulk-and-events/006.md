# Task: POST /files/mutate/batch

## Description

The vertical slice that makes bulk upload usable: the endpoint that joins the multipart reader
(002), the batch session (004) and the ZIP writer (005), with its limits and OpenAPI metadata.

## Context for the implementer

- HTTP surface, limits and headers: `.claude/epics/bulk-and-events/contracts.md`.
- Request-level checks, before the first response byte: not multipart (400), Content-Length
  over `MaxBatchBytes` (413), zero file parts (400), concurrency limit (429). After the first
  entry is written the status is committed; later problems become manifest rows, and a
  malformed multipart or a client disconnect ends the archive with `complete: false` where
  possible and `session.Abort(...)`.
- Body size: Kestrel's global `MaxRequestBodySize` is set in `Program.cs` to one file plus
  overhead (about 10 MiB). The batch endpoint must raise it for itself via
  `IHttpMaxRequestBodySizeFeature` before reading the body, and must not raise it globally.
- Concurrency limit: built-in `Microsoft.AspNetCore.RateLimiting` concurrency limiter,
  `MaxConcurrentBatches`, `QueueLimit = 0`, rejection 429 as ProblemDetails, applied to this
  endpoint only (ADR-0011).
- `X-Batch-Id` header and `Content-Disposition: attachment; filename="batch-<id>.zip"` are set
  before the first write. Deferred to 007: `GET /batches/{id}`.
- OpenAPI: `MutateBatchRequest` with `IFormFileCollection Files` under form field `files`; use
  the finding from story 005 about Scalar's multi-file rendering.
- Register `IBatchMutationService` and bind the new `Upload` keys in `Program.cs`, with
  `ValidateOnStart` rules like the existing ones.

## Pre-mortem

**Most likely failure:** a file fails after the 200 is committed and the handler tries to
return a ProblemDetails, producing a corrupt archive and an exception in the log.

**Early signal:** any `return Problem(...)` reachable after `ZipBatchResponseWriter.CreateAsync`.

**Kill criterion:** if the diff passes ~400 LOC of code, move the rate limiter and its tests to
a follow-up story before continuing.

## Acceptance Criteria
- [ ] 3 valid files return 200 `application/zip` with 3 mutated entries under their names plus `manifest.json` last
- [ ] A planted mutator that throws on file 2 of 3: archive has files 1 and 3, manifest marks 2 `MutationFailed`, status 200
- [ ] A `.json` among `.txt` files is a manifest row, not a 415
- [ ] Not multipart 400, no files 400, Content-Length over `MaxBatchBytes` 413, all ProblemDetails
- [ ] A batch between 10 MiB and `MaxBatchBytes` is accepted; the single-file endpoint still rejects 10 MiB + 1 file
- [ ] With `MaxConcurrentBatches = 1`, a second concurrent request gets 429
- [ ] `POST /files/mutate` tests pass unmodified
- [ ] Each new test fails against a planted defect (listed in the PR)
