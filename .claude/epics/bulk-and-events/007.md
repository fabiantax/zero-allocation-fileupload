# Task: Batch status read model behind GET /batches/{id}

## Description

The query side of CQRS and the first real listener: a projection that builds batch progress
from events, served by `GET /batches/{id}`. Also the end-to-end proof that chaining works
through the real HTTP path.

## Context for the implementer

- Signatures: `.claude/epics/bulk-and-events/contracts.md`, `BatchStatusProjection` section.
- Register the projection for all five event types with `AddEventHandler` (story 003 makes that
  one instance). Bind `BatchStatusOptions` from an `EventBus:Status` config section.
- Bounds: at most `MaxTrackedBatches` entries; an entry expires `TimeToLive` after its last
  event, measured with the injected `TimeProvider`. `tests/FileMutation.TestCommon` only has a
  fixed `FixedTimeProvider` and is owned by v0.2 story #104, so write a small advanceable
  `TimeProvider` fake inside this story's test file. When full, evict the entry with the
  oldest last event.
- Response: counts and state only, never file names. Unknown or expired id: 404; malformed id:
  400. Add `BatchStatus` to `ApiJsonSerializerContext` in `Program.cs`.
- Status is eventually consistent: events are processed in the background, so a GET right
  after the upload may lag. Tests poll with a timeout, never `Task.Delay` guesses.
- End-to-end chain test: register a recording `IEventHandler<BatchEvent subtype>` in the test
  factory, upload 25 files with `ChunkSize` 10, and assert the recorder saw 25 file events, 3
  chunk events (10, 10, 5) and one `BatchCompleted`, in sequence order.

## Pre-mortem

**Most likely failure:** the projection is updated from the dispatcher thread while the
endpoint reads it, and a torn read returns counts from two different events.

**Early signal:** a concurrent test (reader loop plus 1,000 events) sees `Mutated + Rejected`
decrease between reads.

**Kill criterion:** use immutable `BatchStatus` records swapped atomically in a
`ConcurrentDictionary`; no fine-grained locking.
