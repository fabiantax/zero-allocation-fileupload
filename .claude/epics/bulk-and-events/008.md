# Task: Batch allocation benchmark and README

## Description

Prove the one-file-in-memory claim with a measurement, and surface v0.3 in the README without
touching the existing 784-792 B per-operation headline.

## Context for the implementer

- Model: `benchmarks/FileMutation.Benchmarks/MutationBenchmarks.cs` and
  `docs/benchmarks/allocation-results.md` (exact command, tool and runtime versions, table,
  then an honest paragraph about what the numbers do and do not show).
- New `BatchBenchmarks`: `[MemoryDiagnoser]`, parameters files = 1, 10, 100 at 1 KiB and
  256 KiB each, driving `BatchMutationSession` plus `ZipBatchResponseWriter` into
  `Stream.Null`. Report allocated bytes per batch and per file.
- Report the ZIP writer's allocation separately (a run with a pass-through writer), because
  Deflate allocates its own buffers. The per-file mutation figure and the ZIP figure are
  different numbers and must never be summed into the headline.
- README: a short "Bulk upload and batch events (v0.3)" section: endpoint, manifest, events,
  delivery guarantee in one sentence, link to ADR-0011/0012 and the results page. The unit is
  "per file" or "per batch", never "per request".

## Files

- `benchmarks/FileMutation.Benchmarks/BatchBenchmarks.cs` (new)
- `docs/benchmarks/batch-results.md` (new)
- `README.md`

## Pre-mortem

**Most likely failure:** allocation grows with file count because of the outcome list and
event records, and the results page calls it "flat" anyway.

**Early signal:** per-file bytes at 100 files more than 10% above per-file bytes at 10 files.

**Kill criterion:** publish the measured numbers as they are and file the growth as an issue
against story 004; never tune the benchmark to hide it.
